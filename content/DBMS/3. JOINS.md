# What are Joins?

A **JOIN** is used to combine rows from two or more tables based on a related column.

Example:

### Users Table

|id|name|
|---|---|
|1|John|
|2|Jane|

### Orders Table

|id|user_id|amount|
|---|---|---|
|101|1|500|
|102|1|300|
|103|2|700|

To get user details along with orders:

```sql
SELECT
    u.name,
    o.amount
FROM users u
JOIN orders o
    ON u.id = o.user_id;
```

Result:

|name|amount|
|---|---|
|John|500|
|John|300|
|Jane|700|

---

# Types of Joins

## INNER JOIN

Returns matching records only.

```sql
SELECT *
FROM users u
INNER JOIN orders o
ON u.id = o.user_id;
```

```
Users ∩ Orders
```

---

## LEFT JOIN

Returns all rows from left table.

```sql
SELECT *
FROM users u
LEFT JOIN orders o
ON u.id = o.user_id;
```

Even users without orders appear.

---

## RIGHT JOIN

Returns all rows from right table.

```sql
SELECT *
FROM users u
RIGHT JOIN orders o
ON u.id = o.user_id;
```

---

## FULL OUTER JOIN

Returns everything from both tables.

```sql
SELECT *
FROM users u
FULL OUTER JOIN orders o
ON u.id = o.user_id;
```

---

# What is a Nested Join?

A nested join means joining many tables together.

Example:

```sql
SELECT *
FROM users u
JOIN orders o
    ON u.id = o.user_id
JOIN payments p
    ON o.id = p.order_id
JOIN products pr
    ON o.product_id = pr.id
JOIN categories c
    ON pr.category_id = c.id
JOIN reviews r
    ON pr.id = r.product_id;
```

Tables:

```
Users
 ↓
Orders
 ↓
Payments
 ↓
Products
 ↓
Categories
 ↓
Reviews
```

---

# Why Are Nested Joins Problematic?

## 1. Performance Issues

Suppose:

```
Users      = 1 Million
Orders     = 10 Million
Products   = 500K
Reviews    = 20 Million
```

Database may need to:

```
Scan
Sort
Hash
Merge
```

across multiple huge datasets.

Query becomes expensive.

---

## 2. Row Explosion

Example:

User:

```
John
```

Orders:

```
3 orders
```

Each order has:

```
5 products
```

Each product has:

```
10 reviews
```

Result rows:

```
1 × 3 × 5 × 10
=
150 rows
```

A single user becomes 150 rows.

This is called a **Cartesian multiplication effect**.

---

## 3. High Memory Usage

Database may create:

```
Hash Tables
Temporary Tables
Sort Buffers
```

Large joins can consume significant memory.

---

## 4. Slow API Responses

```
API Request
     ↓
Complex Join
     ↓
5-10 Seconds
     ↓
Timeout
```

Users experience slow responses.

---

## 5. Hard to Maintain

Example:

```sql
SELECT ...
FROM users
JOIN orders
JOIN products
JOIN reviews
JOIN categories
JOIN inventory
JOIN suppliers
JOIN warehouses
```

Difficult to:

- Read
- Debug
- Optimize

# Example Interview Scenario

### Bad Query

```sql
SELECT *  
FROM users u  
JOIN orders o ON u.id = o.user_id  
JOIN payments p ON o.id = p.order_id  
JOIN products pr ON o.product_id = pr.id  
JOIN reviews r ON pr.id = r.product_id;
```

Problems:

```
Large result set
Duplicate rows
Heavy CPU
Heavy Memory
```

# Better Approaches

## 1. Fetch Only Required Columns

Bad:

```sql
SELECT *
```

Good:

```sql
SELECT
    u.id,
    u.name,
    o.amount
```

Reduces data transfer.

---

## 2. Use Pagination

Bad:

```sql
SELECT *
FROM orders;
```

Good:

```sql
SELECT *
FROM orders
LIMIT 50 OFFSET 0;
```

---

## 3. Separate Queries

Instead of:

```sql
Users
JOIN Orders
JOIN Reviews
JOIN Products
```

Do:

```
Query 1 → User
Query 2 → Orders
Query 3 → Reviews
```

Then combine in application logic when appropriate.

---

## 4. Use Aggregation

Instead of fetching all reviews:

```sql
SELECT *
```

Fetch:

```sql
SELECT
    product_id,
    COUNT(*) review_count
FROM reviews
GROUP BY product_id;
```

---

## 5. Proper Indexing

Indexes on:

```
user_id
order_id
product_id
```

allow joins to execute efficiently.

Example:

```sql
CREATE INDEX idx_orders_user_id
ON orders(user_id);
```

# ORM Example (Prisma)

Bad:

```js
await prisma.user.findMany({
  include: {
    orders: {
      include: {
        products: {
          include: {
            reviews: true
          }
        }
      }
    }
  }
});
```

Can generate multiple joins and huge payloads.

Better:

```js
await prisma.user.findMany({
  select: {
    id: true,
    name: true
  }
});
```

Then fetch related data separately if needed.

# Common Interview Question

### Q: Should we avoid joins?

**Answer:**

No.

Joins are fundamental and often the correct solution.

We should avoid **unnecessary deep joins across many large tables**, especially when:

- Fetching excessive data
- Creating row explosions
- Causing slow queries

---

### Q: When are joins perfectly fine?

Examples:

```
Users JOIN Orders
Orders JOIN Payments
```

With proper indexes and moderate data sizes, joins are efficient.

---

# Senior-Level Interview Answer

Joins are used to combine related data from multiple tables based on matching keys. They are essential in relational databases and are generally efficient when supported by proper indexes. However, deeply nested joins across multiple large tables can lead to row multiplication, excessive memory consumption, complex execution plans, and slow query performance. In production systems, I avoid unnecessary nested joins by selecting only required columns, using pagination, leveraging aggregation, ensuring proper indexing, and sometimes splitting data retrieval into multiple optimized queries. The goal is not to avoid joins entirely, but to use them judiciously and monitor query execution plans for performance bottlenecks.
