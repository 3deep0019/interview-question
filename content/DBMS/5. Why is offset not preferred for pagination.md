Three reasons — hit all three:

**1. Performance degrades linearly with page depth**

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```

Postgres/MySQL has to **scan and discard the first 100,000 rows** before returning the next 20. Page 5,000 is dramatically slower than page 1. On a large table this is O(N) per query — deep pagination cripples the DB.

Cursor-based pagination:

```sql
SELECT * FROM orders 
WHERE created_at < '2026-07-31T10:00:00Z' 
ORDER BY created_at DESC 
LIMIT 20;
```

The `WHERE` uses the index on `created_at` — the DB seeks directly to that key and reads 20 rows. **O(log N)** regardless of how deep you are.

**2. Correctness — rows shift under you**

If new rows are inserted (or deleted) between page requests, **offset skips or duplicates rows**.

- User loads page 1 (offset 0, rows 1–20).
- 5 new rows get inserted at the top.
- User clicks "next" → offset 20 → server returns what were originally rows 15–34 → **rows 15–20 appear twice**.

Cursor pagination anchors on a value from the last row you saw (`last_id`, `last_created_at`), so shifts don't corrupt the sequence. Users see a stable feed.

**3. It leaks total count and enables enumeration abuse**

- Offset UIs usually expose "page X of Y," which means the server has to run a `COUNT(*)` — another expensive query on big tables.
- If your resources are auto-incremented IDs and you allow arbitrary offset, someone can enumerate the entire dataset with a script. Cursors that are opaque (`base64(created_at + id)`) make this harder.

**When offset IS fine:**

- Small datasets (<10k rows).
- Admin tables where users genuinely want "jump to page 47."
- Reports where the dataset is frozen (snapshot exports).

**When cursor is required:**

- Feeds, activity streams, real-time data (Twitter, Slack, GitLab activity — all cursor-paginated).
- Any table that will grow into six figures.
- Anywhere the UI is infinite scroll.

**One-liner to land it:**  
_"Offset costs the database more the deeper you go and returns wrong data when the underlying set is changing. Cursor pagination is O(log N) via index seek and gives a stable view even with concurrent writes — that's what I'd default to for anything user-facing at scale."_
