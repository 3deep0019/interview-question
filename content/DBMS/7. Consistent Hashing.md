A good way to understand consistent hashing is to see how keys move as servers are added or removed.

## 1. Traditional Hashing (Modulo)

Suppose we have 4 servers:

```
hash(key) % 4

           +---------+
           | Request |
           +---------+
                |
                v
      hash(key) % 4
                |
     ---------------------
     |    |    |    |
    S0   S1   S2   S3
```

Example:

|Key|Hash|`%4`|Server|
|---|---|---|---|
|A|21|1|S1|
|B|37|1|S1|
|C|45|1|S1|
|D|52|0|S0|

Now suppose we add another server.

```
hash(key) % 5
```

Almost **every key changes servers**, causing a massive cache miss or data migration.

---

# 2. Consistent Hashing Ring

Instead of modulo, imagine the hash space arranged in a circle.

```
                  0
             /         \
         10             250
       /                   \
     20                     230
    /                         \
 40                             210
 |                               |
 |                               |
 60                             180
   \                           /
      90                  160
          \            /
              128
```

Hash values wrap around.

---

## 3. Place Servers on the Ring

Servers are hashed too.

```
                    (0)
                      |
          S1          |
       (30)           |
                      |
                      |
      User Keys       |
                      |
S2(110)               |
                      |
                      |
                      |
             S3(210)
```

Example

```
S1 -> hash = 30
S2 -> hash =110
S3 -> hash =210
```

---

## 4. Place Keys

Keys also get hashed.

```
                    0
                    |
          K1=20
                    |
      S1=30
                    |
          K2=50
                    |
          K3=80
                    |
      S2=110
                    |
          K4=150
                    |
      S3=210
                    |
          K5=240
                    |
          wraps back
```

---

## 5. Assignment Rule

Move **clockwise** until the first server.

Example

```
K1 =20

20 ---------> 30

Stored in S1
```

```
K2 =50

50 --->110

Stored in S2
```

```
K3 =80

80 --->110

Stored in S2
```

```
K4 =150

150 --->210

Stored in S3
```

```
K5 =240

240 ---> wraps --->30

Stored in S1
```

Final mapping

|Key|Stored In|
|---|---|
|K1|S1|
|K2|S2|
|K3|S2|
|K4|S3|
|K5|S1|

---

# 6. Add a New Server

Suppose a new server appears.

```
S4 =170
```

Before

```
110 -----------210

          S3
```

After

```
110 -----170------210

      S4      S3
```

Only the keys between **110 and 170** move.

```
Before

K4=150 -> S3

After

K4=150 -> S4
```

Everything else stays exactly where it was.

This is the biggest advantage of consistent hashing.

---

# 7. Remove a Server

Suppose S2 crashes.

Before

```
S1(30)

      |

S2(110)

      |

S3(210)
```

Keys on S2

```
K2
K3
```

After removal

```
K2
K3

move clockwise

↓

S3
```

Only S2's keys move.

---

# 8. Problem: Uneven Distribution

Suppose

```
S1 =20
S2 =25
S3 =220
```

```
20----25---------------------------220
```

Now

```
S2 owns tiny range

S3 owns huge range
```

Load becomes very uneven.

---

# 9. Virtual Nodes (VNodes)

Instead of placing one point per server, place many.

Example

```
Physical Server A

A1
A2
A3
A4

Physical Server B

B1
B2
B3
B4

Physical Server C

C1
C2
C3
C4
```

Ring

```
A1
      B1
            C1
                  A2
                        C2
                              B2
                                     A3
                                           C3
                                                 B3
                                                      A4
                                                           C4
                                                               B4
```

Now each physical server owns many small ranges.

Benefits:

- Even load distribution
- Better fault tolerance
- Easier scaling
- Smooth rebalancing

---

# 10. Real-World Example (Redis Cluster)

Suppose you have:

```
Redis-1
Redis-2
Redis-3
```

A user cache key

```
user:125
```

gets hashed

```
hash(user:125)=145
```

Ring

```
110 (Redis-2)

145

170 (Redis-4)

210 (Redis-3)
```

If Redis-4 is added, only keys in the range **110–170** move to Redis-4. The rest of the cluster is unaffected.

# 11. Why Big Companies Use It

|System|Usage|
|---|---|
|Amazon DynamoDB|Partitioning data across nodes|
|Apache Cassandra|Data distribution|
|Redis Cluster|Slot-based partitioning inspired by consistent hashing principles|
|Memcached|Distributed caching|
|NGINX|Sticky sessions / upstream selection (depending on configuration)|

# 12. Interview Summary

```
Traditional Hashing
-------------------

hash(key) % N

Add one server
↓

Almost every key moves ❌


Consistent Hashing
------------------

Hash servers
Hash keys

Arrange on ring

Key moves clockwise

↓

Only affected partition moves ✅

↓

Add server
↓

Small number of keys move

↓

Remove server
↓

Only that server's keys move

↓

Use Virtual Nodes

↓

Balanced load
```

### Complexity

|Operation|Complexity|
|---|---|
|Find server for a key|O(log N) using a sorted map (or O(1) average with specialized structures)|
|Add server|O(log N) plus reassignment of affected keys|
|Remove server|O(log N) plus reassignment of affected keys|
|Memory|O(number of virtual nodes)|

For senior backend interviews, it's common to follow this explanation by implementing a consistent hash ring using a sorted map (or a `TreeMap` in Java, a balanced tree, or a sorted array with binary search in Node.js/TypeScript), then extending it with virtual nodes.
