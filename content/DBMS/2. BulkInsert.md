# How would you handle or use bulk insert and insert over and over again?

# Interview Answer

 If I need to insert a large number of records, I prefer bulk inserts instead of inserting one row at a time. Bulk inserts reduce database round trips, lower transaction overhead, improve throughput, and reduce connection usage. For very large datasets, I process records in batches and use transactions to ensure consistency.

---

# Bad Approach: Insert One By One

```js
for (const user of users) {
  await prisma.user.create({
    data: user
  });
}
```

### Problem

If there are:

```
100,000 records
```

Then:

```
100,000 Database Calls
100,000 Network Round Trips
100,000 Transactions
```

Very slow.

---

# Better Approach: Bulk Insert

### Prisma

```js
await prisma.user.createMany({
  data: users
});
```

### SQL

```sql
INSERT INTO users(name,email)
VALUES
('John','john@test.com'),
('Jane','jane@test.com'),
('Bob','bob@test.com');
```

Benefits:

```
1 Query
1 Transaction
Less Network Overhead
```

# Large Dataset Example

Suppose:

```
10 Million Records
```

Don't do:

```js
createMany(10 million rows)
```

Because:

```
Memory Issues
Huge Transaction
Lock Contention
```

---

## Batch Processing

```js
const BATCH_SIZE = 1000;

for (let i = 0; i < users.length; i += BATCH_SIZE) {

    const batch = users.slice(i, i + BATCH_SIZE);

    await prisma.user.createMany({
        data: batch
    });
}
```

Flow:

```
1000 Records
     ↓
Bulk Insert
     ↓
Next 1000
     ↓
Bulk Insert
```

---

# Processing a 10GB CSV

```
CSV File
     ↓
Read Stream
     ↓
Collect 1000 Rows
     ↓
Bulk Insert
     ↓
Clear Memory
     ↓
Continue
```

Example:

```js
let batch = [];

stream.on('data', async row => {

   batch.push(row);

   if (batch.length === 1000) {

      stream.pause();

      await prisma.user.createMany({
         data: batch
      });

      batch = [];

      stream.resume();
   }
});
```

# Transaction Usage

If all inserts must succeed together:

```js
await prisma.$transaction([
  prisma.user.createMany({ data: users }),
  prisma.profile.createMany({ data: profiles })
]);
```

Benefits:

```
All Success
OR
All Rollback
```

---

# PostgreSQL COPY (Fastest)

For millions of rows:

```sql
COPY users(name,email)
FROM '/tmp/users.csv'
DELIMITER ','
CSV HEADER;
```

Much faster than individual inserts.

Performance:

```
Single Inserts      → Slow
Bulk Insert         → Faster
COPY Command        → Fastest
```

# Common Interview Follow-ups

### Q: Why is bulk insert faster?

**Answer:**

Because it reduces:

- Network round trips
- Transaction creation overhead
- Database parsing and execution costs

---

### Q: How many records should be inserted per batch?

**Answer:**

Depends on the database and row size, but common values are:

```
500
1000
5000
10000
```

I usually start with **1000 rows per batch** and benchmark.

---

### Q: What if one row in a batch is invalid?

Options:

1. Reject the entire batch.
2. Validate before insert.
3. Use database features like:

```sql
ON CONFLICT DO NOTHING
```

or

```sql
ON CONFLICT DO UPDATE
```

---

### Q: How would you insert 10 million rows?

**Answer:**

1. Store file in S3/GCS.
2. Stream file in chunks.
3. Batch records (1000–5000 rows).
4. Use bulk inserts or PostgreSQL COPY.
5. Process through worker services/queues.
6. Monitor failures and retry batches.

# Senior-Level Answer (1 Minute)

For large-scale inserts, I avoid inserting records one by one because it creates excessive database round trips and transaction overhead. Instead, I use bulk inserts with batching, typically 1000–5000 records per batch depending on payload size and database limits. For file imports, I stream the file, accumulate records into batches, and perform bulk inserts while controlling memory usage. For very large datasets, such as millions of records, I prefer database-native mechanisms like PostgreSQL COPY and process data asynchronously through queues such as Kafka or BullMQ. This approach improves throughput, reduces database load, and scales reliably under high-volume workloads.
