A **Database Trigger** is a special stored procedure that automatically executes when a specific event occurs on a table or view.

Common events:
- `INSERT`
- `UPDATE`
- `DELETE`

Think of it as:

```
Table Event Occurs
       ↓
Trigger Fires Automatically
       ↓
Execute Logic
```

---

# Interview Answer

```
A database trigger is a database object that automatically executes predefined logic when specific events such as INSERT, UPDATE, or DELETE occur on a table. Triggers are commonly used for auditing, logging, validation, maintaining history tables, and enforcing business rules.
```

---

# Example Scenario

Suppose you have:

```sql
users
-----
id
name
email
```

And an audit table:

```sql
user_audit
----------
user_id
action
created_at
```

Whenever a new user is inserted, you want to log it automatically.

---

# Trigger Example (PostgreSQL)

### Trigger Function

```sql
CREATE OR REPLACE FUNCTION log_user_insert()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO user_audit(
        user_id,
        action,
        created_at
    )
    VALUES(
        NEW.id,
        'INSERT',
        NOW()
    );

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

---

### Create Trigger

```sql
CREATE TRIGGER user_insert_trigger
AFTER INSERT ON users
FOR EACH ROW
EXECUTE FUNCTION log_user_insert();
```

Now:

```sql
INSERT INTO users(name,email)
VALUES('John','john@test.com');
```

Automatically inserts:

```sql
user_id | action | created_at
--------------------------------
1       | INSERT | ...
```

# BEFORE vs AFTER Trigger

## BEFORE Trigger

Runs before data is written.

```
INSERT Request
      ↓
BEFORE Trigger
      ↓
Table Update
```

Example:

```sql
CREATE TRIGGER validate_salary
BEFORE INSERT
ON employees
```

Use cases:

- Validation
- Data transformation
- Default values

---

## AFTER Trigger

Runs after data is saved.

```
INSERT Request
      ↓
Save Data
      ↓
AFTER Trigger
```

Use cases:

- Audit logs
- Notifications
- History tracking

# NEW and OLD Keywords

### NEW

Represents new data.

```sql
NEW.name
NEW.email
```

Example:

```sql
INSERT INTO users
VALUES(1,'John');
```

`NEW.name = 'John'`

---

### OLD

Represents existing data before update/delete.

```sql
OLD.name
```

Example:

```sql
UPDATE users
SET name='Jane'
WHERE id=1;
```

```sql
OLD.name = John
NEW.name = Jane
```

# Update Audit Example

```sql
CREATE OR REPLACE FUNCTION track_email_change()
RETURNS TRIGGER AS $$
BEGIN

    INSERT INTO user_audit(
      user_id,
      action
    )
    VALUES(
      OLD.id,
      'EMAIL_UPDATED'
    );

    RETURN NEW;
END;

$$ LANGUAGE plpgsql;
```

Trigger:

```sql
CREATE TRIGGER email_change_trigger
AFTER UPDATE
ON users
FOR EACH ROW
WHEN (OLD.email IS DISTINCT FROM NEW.email)
EXECUTE FUNCTION track_email_change();
```

# Advantages

### Data Integrity

Rules enforced regardless of application.

```
Node App
Python App
Java App
```

All follow the same rule.

---

### Automatic Execution

No developer can forget to run it.

---

### Centralized Logic

Business rule exists in one place.

---

# Disadvantages

### Hidden Logic

A developer runs:

```sql
INSERT INTO users...
```

But additional actions happen automatically.

Harder to debug.

---

### Performance Impact

Every insert/update/delete may execute extra queries.

Example:

```
1M inserts
    ↓
1M trigger executions
```

Can become slow.

---

### Hard to Version Control

Application code is easier to track than database triggers.

---

# Modern Architecture Consideration

In microservices, many teams prefer:

```
DB Change
    ↓
Event Published
    ↓
Kafka/RabbitMQ
    ↓
Consumers
```

instead of heavy trigger usage.

Reason:

- Easier debugging
- Better scalability
- Clear ownership

# Common Interview Questions

### Q: Difference between Trigger and Stored Procedure?

|Trigger|Stored Procedure|
|---|---|
|Runs automatically|Called manually|
|Event-driven|Explicit execution|
|INSERT/UPDATE/DELETE based|Any business logic|

Example:

```sql
CALL process_order();
```

Stored Procedure.

```sql
AFTER INSERT
```

Trigger.

---

### Q: Can a trigger call another trigger?

Yes.

Example:

```
Insert User
     ↓
Trigger A
     ↓
Insert Audit
     ↓
Trigger B
```

This is called cascading triggers.

---

### Q: Why should triggers be used carefully?

Because:

- Hidden behavior
- Hard debugging
- Performance overhead
- Risk of recursive executions

# Senior-Level Interview Answer

```
A database trigger is an event-driven database object that automatically executes when INSERT, UPDATE, or DELETE operations occur on a table. Triggers are commonly used for auditing, maintaining history tables, enforcing data integrity, and updating derived data. While they provide centralized enforcement of business rules, excessive trigger usage can lead to hidden side effects, performance overhead, and maintenance challenges. In modern systems, I typically reserve triggers for auditing and integrity-related concerns, while business workflows are often handled through application services or event-driven architectures.
```
