**Definitions first (they'll expect the distinction):**

**Debounce** — wait until the events _stop_ for N ms, then fire once.

- Use case: **search-as-you-type**. Fire the API call 300ms after the user stops typing, not on every keystroke.
- User types "electronic" → one call, not nine.

**Throttle** — fire at most once every N ms, regardless of how many events come in.

- Use case: **scroll, resize, mousemove**. Fire every 100ms even while the events keep coming.
- User scrolls continuously → 10 calls/second, not 60.

**One-line memorization:** _Debounce fires at the end of the burst; throttle fires at a fixed rate during the burst._

**Implementations:**

```js
// Debounce
function debounce(fn, ms) {
  let t;
  return (...args) => {
    clearTimeout(t);
    t = setTimeout(() => fn(...args), ms);
  };
}

// Throttle (leading edge + trailing tail)
function throttle(fn, ms) {
  let last = 0, timer;
  return (...args) => {
    const now = Date.now();
    const remaining = ms - (now - last);
    if (remaining <= 0) {
      clearTimeout(timer); timer = null;
      last = now; fn(...args);
    } else if (!timer) {
      timer = setTimeout(() => { last = Date.now(); timer = null; fn(...args); }, remaining);
    }
  };
}
```

Prefer battle-tested versions: `lodash.debounce`, `lodash.throttle`.

**Real-world patterns for "too much data in the frontend":**

**1. Debounced search input**

```js
const search = debounce(async (query) => {
  const results = await api.search(query);
  setResults(results);
}, 300);
```

Always **cancel stale requests** with `AbortController` — a slow response to "elec" shouldn't overwrite the fresh response to "electronics":

```js
let controller;
const search = debounce(async (query) => {
  controller?.abort();
  controller = new AbortController();
  try {
    const results = await api.search(query, { signal: controller.signal });
    setResults(results);
  } catch (e) {
    if (e.name !== 'AbortError') throw e;
  }
}, 300);
```

**2. Throttled scroll / resize handlers**

```js
window.addEventListener('scroll', throttle(() => {
  updateHeaderVisibility();
  recordScrollDepth();
}, 100), { passive: true });
```

The `passive: true` tells the browser you won't `preventDefault` — scroll stays smooth.

**Modern alternative:** replace scroll listeners entirely with `IntersectionObserver` (element in viewport?) and `ResizeObserver` (element resized?). Browser-native, zero throttling logic needed. This is the answer that impresses interviewers — "I'd use IntersectionObserver instead of a throttled scroll handler."

**3. Batching writes**  
For analytics events, chat message send, autosave — buffer events client-side, flush every N ms or when the buffer hits M entries. This is throttling applied to _output_, not _input_.

**4. Windowing for rendering**  
If the "too much data" is a 20k-row list — debounce/throttle don't help. Use virtualization (`TanStack Virtual`, `vue-virtual-scroller`) so only the visible ~30 rows render. Different tool, different problem, worth calling out that you know the difference.

**5. requestAnimationFrame throttling (for visual updates)**  
For handlers that update the DOM on every event (drag, scroll parallax), throttle to the frame rate — one update per frame max:

```js
let ticking = false;
window.addEventListener('scroll', () => {
  if (!ticking) {
    requestAnimationFrame(() => { updateUI(); ticking = false; });
    ticking = true;
  }
});
```

**6. Web Workers for heavy compute**  
If "too much data" means computing over 20k rows on the client (sort, aggregate, chart), offload to a Web Worker. Keeps the main thread at 60fps.

**Practical checklist I'd give in the interview:**

- **Input events** (typing, search) → debounce ~300ms + AbortController on stale requests.
- **Continuous events** (scroll, mousemove, resize) → throttle ~100ms, or better, `IntersectionObserver` / `ResizeObserver`.
- **Visual updates on scroll/drag** → `requestAnimationFrame`.
- **Rendering large lists** → virtualization, not debouncing.
- **Client-side heavy compute** → Web Worker.
- **Outbound network** → batch + `sendBeacon` on unload.
- **Server-side always does the filter/sort/search** for 20k+ datasets — don't try to handle them all in the browser.

**Land it:**

_"Debounce for user input where I care about the final value — 300ms with AbortController on the last request. Throttle for continuous events at ~100ms, but I default to IntersectionObserver and ResizeObserver over throttled scroll handlers when the browser gives me a native option. And to be clear — debounce and throttle solve the 'too many events' problem, not the 'too much data on screen' problem. That's virtualization. Different tool per problem is what shows you've built this before."_
