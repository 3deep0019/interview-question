## How would you process a large file (e.g 10 GB ) without blocking the event loop or running out of memory and store that data in table or cloud storage.

For a **10GB file**, I would never load the entire file into memory using `fs.readFile()`. Instead, I'd use **Node.js Streams** to read the file in chunks, process each chunk incrementally, and either:

1. Store parsed records in a database using **batch inserts**.
2. Upload the file directly to cloud storage using **streaming uploads**.

This keeps memory usage constant, prevents event loop blocking, and scales to very large files.

---

## Scenario 1: 10GB CSV → Database

### Architecture

```
Large CSV File
       ↓
Read Stream
       ↓
CSV Parser Stream
       ↓
Batch Records (1000 rows)
       ↓
Bulk Insert
       ↓
Database
```

### Example

```js
const fs = require('fs');
const csv = require('csv-parser');

const BATCH_SIZE = 1000;
let batch = [];

fs.createReadStream('large.csv')
  .pipe(csv())
  .on('data', async (row) => {
      batch.push(row);

      if (batch.length >= BATCH_SIZE) {
          const currentBatch = batch;
          batch = [];

          // Pause reading
          stream.pause();

          await prisma.users.createMany({
              data: currentBatch
          });

          stream.resume();
      }
  })
  .on('end', async () => {
      if (batch.length) {
          await prisma.users.createMany({
              data: batch
          });
      }
  });
```

## Scenario 2: 10GB File → Cloud Storage

### AWS S3

```js
const fs = require('fs');
const { Upload } = require('@aws-sdk/lib-storage');

const upload = new Upload({
  client: s3Client,
  params: {
    Bucket: 'my-bucket',
    Key: 'large-file.csv',
    Body: fs.createReadStream('large-file.csv')
  }
});

await upload.done();
```

### What Happens?

```
Disk
 ↓
Read Stream
 ↓
Multipart Upload
 ↓
S3
```

The file is uploaded chunk-by-chunk without loading 10GB into memory.

## Scenario 3: Parse File and Upload Processed Data

```
Input File
      ↓
Read Stream
      ↓
Transform Stream
      ↓
Compress
      ↓
Cloud Storage
```

Example:

```js
const { pipeline } = require('stream/promises');
const zlib = require('zlib');

await pipeline(
  fs.createReadStream('large.csv'),
  zlib.createGzip(),
  fs.createWriteStream('large.csv.gz')
);
```

Or replace the write stream with an S3 upload stream.

## Preventing Event Loop Blocking

Reading via streams solves memory issues, but CPU-heavy parsing can still block the event loop.

Bad:

```js
stream.on('data', chunk => {
    performHeavyCalculation(chunk);
});
```

If parsing takes 500ms per chunk:

```
Event Loop Blocked
API Requests Delayed
```

Use:

### Worker Threads

```js
const { Worker } = require('worker_threads');
```

Architecture:

```
Read Stream
      ↓
Chunk
      ↓
Worker Thread
      ↓
Processed Data
      ↓
Database/S3
```

## Production Design for 10GB Import

```
Client Upload
      ↓
Cloud Storage (S3/GCS)
      ↓
Upload Complete Event
      ↓
Queue (Kafka/BullMQ)
      ↓
Worker Service
      ↓
Stream File
      ↓
Validate Data
      ↓
Batch Insert (1000-5000 rows)
      ↓
Database
```

### Why?

- Upload service remains fast.
- Processing can be retried.
- Horizontal scaling possible.
- No memory spikes.
- Suitable for files of 10GB, 50GB, or even 100GB.

## Senior-Level Interview Answer (1 Minute)

```
For a 10GB file, 
I would use Node.js streams to process the file incrementally instead of loading it entirely into memory. 
If the target is a database, I'd parse the stream and perform bulk inserts in batches (e.g., 1000 rows per batch) to reduce database overhead. 
For cloud storage like S3 or GCS, I'd stream the file directly using multipart uploads. 
To avoid blocking the event loop during heavy transformations, I'd offload CPU-intensive work to Worker Threads or background workers. 
In production, I'd typically upload the file to cloud storage first, trigger processing through a queue such as Kafka or BullMQ, and have worker services stream, validate, and store the data. This provides scalability, fault tolerance, low memory usage, and high throughput.
```
