A **Health Check** is a lightweight endpoint or mechanism used to determine whether an application is running correctly and can serve requests.

---

## Simple Interview Answer


A health check is an endpoint that allows load balancers, Kubernetes, monitoring systems, or other services to verify whether an application is healthy and ready to handle traffic.


Example:

```
GET /health
```

Response:

```json
{  
	"status": "UP"
}
```

---

## Why Do We Need It?

Imagine:

```
User
  ↓
Load Balancer
  ↓
Node.js App
```

If one server crashes:

```
Server 1 ✅
Server 2 ❌
Server 3 ✅
```

The load balancer needs a way to know Server 2 is unhealthy and stop sending traffic to it.

That's what health checks are for.

---

## Types of Health Checks

### 1. Liveness Check

**Question:** Is the application process alive?

Used by Kubernetes to determine whether a container should be restarted.

```json
{
  "status": "alive"
}
```

Example:

```
GET /health/live
```

If it fails:

```
Kubernetes → Restart Container
```

---

### 2. Readiness Check

**Question:** Can the application serve requests?

Application might be running but:

- Database disconnected
- Redis unavailable
- Startup still in progress

Example:

```
GET /health/ready
```

Response:

```json
{  
	"status": "ready"
}
```

If not ready:

```
Load Balancer stops routing traffic
```

but the container is not restarted.

---

### 3. Dependency Health Check

Checks external services.

```
Application
   ↓
Database
Redis
S3
Kafka
```

Example response:

```json
{
  "status": "UP",
  "database": "UP",
  "redis": "UP",
  "kafka": "UP"
}
```

## Node.js Example

Using Express:

```js
const express = require('express');

const app = express();

app.get('/health', (req, res) => {
  res.status(200).json({
    status: 'UP',
    timestamp: new Date()
  });
});

app.listen(3000);
```

---

## Real Production Health Check

```js
app.get('/health', async (req, res) => {
  try {
    await prisma.$queryRaw`SELECT 1`;

    res.status(200).json({
      status: 'UP',
      database: 'CONNECTED'
    });
  } catch (err) {
    res.status(503).json({
      status: 'DOWN',
      database: 'DISCONNECTED'
    });
  }
});
```

## Health Check vs Monitoring

|Health Check|Monitoring|
|---|---|
|Is app alive?|Why is app slow?|
|Simple status|Detailed metrics|
|Fast response|Historical analysis|
|`/health` endpoint|Prometheus/Grafana|

Example:

```
Health Check:
"App is running"

Monitoring:
CPU = 95%
Memory = 90%
Response Time = 2s
```

## Follow-up Interview Questions

### Q: Should health checks query the database every time?

**Answer:**  
Not always. Basic liveness checks should be lightweight. Readiness checks can verify critical dependencies such as databases or Redis.

---

### Q: What HTTP status codes should a health endpoint return?

- `200 OK` → Healthy
- `503 Service Unavailable` → Unhealthy

Example:

```
200 OK
```

```
503 Service Unavailable
```

---

### Q: Why separate liveness and readiness probes?

**Answer:**

- **Liveness** determines whether the process should be restarted.
- **Readiness** determines whether traffic should be routed to the instance.

An application may be alive but not ready (e.g., waiting for database connectivity).

---

## Senior-Level Answer

A health check is an endpoint used by load balancers, Kubernetes, and monitoring systems to determine the state of an application. Typically, we implement liveness checks to verify the process is running, readiness checks to ensure the application can serve traffic, and dependency checks to validate services like databases, Redis, or Kafka. Health checks help automate failover, traffic routing, and container restarts, improving system reliability and availability.
