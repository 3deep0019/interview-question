**The pain to avoid:** user hits "Pay" → 401 → dumped to login → cart lost → churn. Never let that happen.

**The layered answer:**

**Layer 1 — Refresh tokens (silent renewal)**

The industry-standard pattern:

- Short-lived **access token** (15 min) + long-lived **refresh token** (7–30 days, HttpOnly cookie).
- Access token in memory or `Authorization` header; refresh token in an **HttpOnly, Secure, SameSite=Strict cookie** — JS can't read it, so XSS can't steal it.
- On 401, the client calls `/auth/refresh`. Server validates the refresh token and issues a new access token. Original request is **retried transparently**.

**Layer 2 — Response interceptor (this is where the checkout-page save happens)**

Axios / fetch interceptor catches the 401, refreshes, retries — user never sees a redirect:

```js
// Axios interceptor
let refreshPromise = null;

api.interceptors.response.use(
  res => res,
  async (err) => {
    const original = err.config;
    if (err.response?.status !== 401 || original._retry) return Promise.reject(err);

    original._retry = true;
    // Dedupe concurrent 401s — all wait on one refresh call
    refreshPromise ??= api.post('/auth/refresh').finally(() => { refreshPromise = null; });
    try {
      await refreshPromise;
      return api(original); // retry the original request
    } catch {
      // Refresh failed → refresh token also expired
      saveCheckoutStateAndRedirectToLogin();
      return Promise.reject(err);
    }
  }
);
```

The `refreshPromise` dedupe is the detail interviewers love — without it, 5 parallel API calls on the checkout page trigger 5 refresh calls and race conditions.

**Layer 3 — Proactive refresh (better UX)**

Don't wait for a 401. Decode the JWT `exp` client-side and **refresh 60 seconds before expiry** via a `setTimeout`. The user never hits the failure path.

**Layer 4 — If refresh also fails (session truly dead)**

This is the checkout-specific piece:

1. **Persist the cart** to `localStorage` (or better, to the server as an abandoned cart tied to the user email).
2. **Persist the checkout form state** — shipping address, chosen payment method (not card details — never touch those, PCI).
3. Show a modal: _"Your session expired — sign in to complete your order."_ Not a full redirect that loses context.
4. After re-auth, **rehydrate the checkout state** and land the user back on the same step.

**Layer 5 — Server-side idempotency**

The user might click "Pay" twice during the reauth dance. Send an **idempotency key** (client-generated UUID) with the payment request so the server dedupes — a retried charge doesn't double-charge.

**Land it:**

_"For checkout specifically — silent refresh via interceptor is the default path so the user never notices. If refresh also fails, I save the cart and form state to localStorage, prompt reauth in a modal, and rehydrate on the way back. And the payment call carries an idempotency key so the retry after refresh doesn't double-charge — that's non-negotiable for money flows."_
