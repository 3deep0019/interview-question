_Role-Based Access Control — permissions attached to roles, roles attached to users. Instead of checking 'is this user Alice', you check 'does this user have the `admin` role'. Scales cleanly as user count grows."_

**How I implemented it at E9 (concrete):**

- Roles live on the user record in Mongo, populated at login by Passport after the SAML/Okta assertion.
- The role gets attached to the session (Redis-backed), so every request has `req.user.roles` available.
- A tiny middleware factory guards routes:

```js
const requireRole = (...allowed) => (req, res, next) => {
  if (!req.user) return res.status(401).end();
  const roles = req.user.roles || [];
  if (!allowed.some(r => roles.includes(r))) return res.status(403).end();
  next();
};

app.get('/admin/reports', requireRole('admin', 'auditor'), reportsHandler);
```

**Points that separate a good answer from a great one:**

- **Enforce on the server, always.** UI hiding a button is UX, not security.
- **Prefer permissions over roles for fine-grained checks** — roles are a bundle of permissions, and route guards should ideally check the permission (`can:reports.read`) not the role. Keeps role definitions flexible without rewriting middleware.
- **Deny by default** — the default state of a route should require an explicit permission.
- **Multi-tenant twist** — at E9 we scoped roles per tenant, so the check is `roles[tenantId].includes('admin')`, not global.
- Related: **ABAC** (Attribute-Based) — check attributes like ownership (`resource.ownerId === user.id`). RBAC + ABAC together covers most real-world needs.
