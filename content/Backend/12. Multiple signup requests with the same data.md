Rate limiter is one layer. There are several others — **defense in depth**:

**1. Database-level uniqueness (the actual source of truth)**

```sql
CREATE UNIQUE INDEX users_email_unique ON users (LOWER(email));
```

Or Mongo:

```js
db.users.createIndex({ email: 1 }, { unique: true, collation: { locale: 'en', strength: 2 } });
```

The DB rejects the duplicate atomically. Everything above this is optimization; this is correctness. **Never rely only on `SELECT` before `INSERT`** — TOCTOU race: two requests both check, both see empty, both insert. Only the unique constraint is race-free.

**2. Idempotency keys**

Client sends `Idempotency-Key: <uuid>` header. Server stores `(key → response)` in Redis with a TTL (24h typical). Same key within TTL returns the cached response, doesn't re-execute. Stripe's model.

```js
async function signup(req, res) {
  const key = req.headers['idempotency-key'];
  const cached = await redis.get(`idem:${key}`);
  if (cached) return res.json(JSON.parse(cached));

  const user = await createUser(req.body);
  await redis.set(`idem:${key}`, JSON.stringify(user), 'EX', 86400);
  res.json(user);
}
```

**3. Distributed lock (Redis `SET NX PX`)**

Grab a short-lived lock keyed by the signup identity — email, phone — for the duration of the request:

```js
const lockKey = `signup:lock:${email.toLowerCase()}`;
const acquired = await redis.set(lockKey, '1', 'NX', 'PX', 5000);
if (!acquired) return res.status(409).json({ error: 'signup in progress' });
try {
  await createUser(...);
} finally {
  await redis.del(lockKey);
}
```

Handles the "user double-clicks Submit" race in <5ms.

**4. CAPTCHA / bot protection**

If the multiple requests are from bots — reCAPTCHA v3 or hCaptcha invisibly scores each signup. High-risk scores get a challenge or hard-block. Doesn't solve accidental duplicates but kills automated abuse.

**5. Email verification (implicit throttle)**

Never activate the account until the user clicks the verification link. Duplicate signups just get another unverified row (or better, the DB rejects the duplicate email). No harm even if 10 come in.

**6. Client-side: disable the button + optimistic loading state**

Cheapest fix, catches 90% of human duplicates:

```js
const [submitting, setSubmitting] = useState(false);
const submit = async () => {
  if (submitting) return;
  setSubmitting(true);
  try { await api.signup(data); } finally { setSubmitting(false); }
};
```

Also handles the tab-close-then-retry case gracefully.

**7. Content-hash dedup (nuclear option for form re-submits)**

Hash the request body (SHA-256 of the JSON) and reject a request with the same hash from the same IP within N seconds. Handles bot signup floods with tiny variations.

**Land it:**

_"Layered — the unique index is the correctness guarantee at the bottom. Above that, idempotency keys make retries safe, a short Redis lock keyed on email handles the double-click race, and the button disables on submit for UX. Rate limiter is the outermost layer against abuse; the rest are the ones that actually give you correctness."_
