**Why cookies (specifically HttpOnly cookies) — the case for:**

1. **HttpOnly means JavaScript can't read it.** `document.cookie` doesn't see it. XSS that runs in the page **cannot exfiltrate the token**. This is the biggest win over `localStorage`, which any XSS can read.
2. **Automatic transmission** — browser sends it on every request to the origin without JS glue.
3. **`Secure` flag** — cookie is only sent over HTTPS, never in plaintext.
4. **`SameSite` flag** — controls cross-site sending. `Strict` blocks CSRF entirely; `Lax` is a good default; `None` requires `Secure` and is for cross-origin APIs.
5. **Scoped** — `Domain` and `Path` limit which requests carry it.

The cookie you want:

```
Set-Cookie: session=<token>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=900
```

**The trade-off — CSRF.** Cookies auto-attach on cross-site requests, so a malicious page can trigger authenticated actions. Mitigations:

- `SameSite=Strict` or `Lax` (mostly kills CSRF).
- **CSRF tokens** for state-changing requests (double-submit cookie pattern or synchronizer token).
- Bearer tokens in headers don't have CSRF risk (browsers don't auto-attach `Authorization`), but they trade CSRF away for XSS exposure.

**Other ways to prevent getting the token / theft:**

**1. Short expiry + refresh tokens**  
Access token lives 15 min. Even if stolen, the window is tight. Refresh tokens rotate (each use invalidates the previous — **refresh token rotation**), so a stolen refresh token gets detected the moment the real user next refreshes (reuse detection → revoke the whole family).

**2. Token binding / fingerprinting**  
Bind the token to a device fingerprint (user-agent hash, IP subnet). Server rejects if the token appears from a mismatched fingerprint. Not bulletproof but raises the bar.

**3. HTTPS everywhere + HSTS**  
`Strict-Transport-Security` header forces the browser to only ever use HTTPS. Kills MITM token theft on public wifi.

**4. Content Security Policy (CSP)**  
Locks down which scripts can run on the page. A strong CSP (`script-src 'self' 'nonce-<random>'`) prevents inline `<script>` injection from executing — kills most XSS at the source. If XSS can't run, it can't steal your token no matter where you store it.

**5. Never in localStorage / sessionStorage for auth**  
Any XSS gets it. `sessionStorage` is only marginally better (tab-scoped). For high-stakes tokens: **HttpOnly cookie or in-memory only**.

**6. In-memory storage (the SPA pattern)**  
Keep the access token in a JS variable, never persisted. Lost on refresh — but you use the HttpOnly refresh cookie to silently re-issue. XSS can grab it if actively running, but nothing to steal after the tab closes.

**7. Backend-for-Frontend (BFF) pattern**  
The token never touches the browser. Browser has a session cookie to your BFF; the BFF holds the real access token and calls upstream APIs on your behalf. Frontend attack surface drops to zero for tokens. **This is the modern best practice for SPAs handling third-party OAuth.**

**8. Rotate on privilege change**  
Regenerate the session on login, on password change, on role elevation. Prevents session fixation.

**9. Secure the origin**

- Sanitize/escape all user-rendered content (React and Vue do this by default — don't `v-html` / `dangerouslySetInnerHTML` untrusted input).
- Sub-resource integrity (`integrity=` on CDN scripts).
- Avoid third-party scripts on authenticated pages when you can.

**Land it:**

_"HttpOnly + Secure + SameSite cookie is the default because it takes the token out of JavaScript's reach — XSS becomes a lot less lucrative. Combine it with short access tokens, refresh rotation with reuse detection, a strong CSP, and HTTPS/HSTS. For SPAs talking to third-party OAuth, I'd go BFF pattern — the token never reaches the browser at all. That's the strongest posture."_
